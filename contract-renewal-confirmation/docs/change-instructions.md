## 現在のRound

### Round 3：基盤構築（IaC雛形・IAM境界・DynamoDBテーブル定義）

**背景**：Round 1で合意した技術設計（アーキテクチャ・データモデル・デプロイ方式）を、実際にデプロイ可能な形の土台として構築する。この土台の上に、Round 4以降の業務ロジックを乗せていく。

**目的**：本番の業務ロジックはまだ実装せず、後続Roundが安全に乗せられるインフラの土台を作り、実際に東京リージョンのAWSアカウントへデプロイできることを確認する。

**依頼内容**：
1. `infra/` に AWS CDK（TypeScript）プロジェクトの雛形を作成する。
2. このプロジェクト専用のIAM境界（permissions boundaryポリシー）を定義し、このプロジェクトで作成する全てのIAMロールへ適用する。既存の業務系・人材評価系リソース（ARN）へは一切アクセスできないよう明示的に制限すること。
3. DynamoDBテーブルを2つ定義する。
   - 現在状態テーブル（対象者ごとの最新状態）
   - 監査ログテーブル（追記専用、状態変化のたびにイベントを記録）
   - どちらも、ステータス別一覧表示・四半期集計に必要なアクセスパターンを想定したGSIを設計すること（詳細な属性設計はここで提案してよい）。
4. 新規CloudFrontディストリビューション＋S3バケットの雛形を作成する。`/*` → S3（プレースホルダページでよい）、`/api/*` → API Gateway（API Gatewayの実体はまだ空でよい）のビヘイビア設定のみ行う。
5. このプロジェクトの全リソースに共通のタグ（例：`Project: contract-renewal`）を付与する設計にする。
6. `cdk deploy` を実際に実行し、東京リージョン（ap-northeast-1）のAWSアカウントへデプロイが成功することを確認する。IAM境界が意図通り機能している（既存リソースへのアクセスが拒否される）ことも確認すること。

**やらないこと**：Lambdaでの業務ロジック実装（週次同期・送信・回答受付等）はまだ行わない。フロントエンドの実UI実装も行わない。API Gatewayの実際のエンドポイント・Lambda統合もまだ行わない（雛形のみ）。

**完了条件**：CDKデプロイが成功し、IAM境界・DynamoDBテーブル・CloudFront/S3雛形が意図通り機能していることが確認され、その結果が報告されること。

## 将来のための申し送り（バックログ）

- **AWSアカウント構成**：当面は既存アカウント内に構築し、後日AWS Organizationsへの移行を検討する（要件定義時点の暫定方針。再検討の余地あり）。
- **送信者表示名のデフォルト**：汎用アシスタント名で確定したが、運用開始後の開封率・返信率のデータを見て見直す余地がある。
- **四半期モニタリングの自動化**：「無反応のまま契約開始日到達」の集計を、将来的にclaude.aiプロジェクトの定期タスク機能で自動化できないか検討する（システム側に参照手段ができてから）。
- **グローバル一時停止スイッチ**：個別の緊急停止とは別に、全体の自動送信を一括で止められる仕組み。要件外の任意提案、実装コスト次第で検討。
- **SES本番送信申請・DNS（SPF/DKIM/DMARC）設定**：Round 6着手前に、社内でDNS設定を行う担当者との調整を早めに始めておくとよい（コーディング外の待ち時間が発生しうるため）。
- **Entra IDアプリ登録（週次同期用、アプリケーション権限）**：管理者の同意が必要な作業のため、Round 3〜4着手前に確認しておく。
- **本人向けリンクのなりすまし対策の最終承認**：要件書8章で未定となっている「最終承認者」の確定が必要。技術的な緩和策（ランダムトークン＋レート制限）は用意する前提だが、リスク受容の最終判断は別途要。
- **個人情報の保持期間・アクセス権限（上長閲覧の要否）**：人事・法務・セキュリティ担当者への確認が必要な論点。技術設計としては保持期間を設定値化し、削除バッチを後付けできる形にする方針のみ決めている。
- **社名normalization overrideの保守運用**：客先都合の社名変更（SCSK等）に気づいた際、誰が `ledger_mapping.json` を更新するかの運用ルールが未定。Round 4以降で軽く検討したい。
